🌊 DATA FLOW DIAGRAMS

Tracing data the way a letter moves through a post office

A DFD doesn't care about buttons or screens — only about where data comes from, where it's processed, where it's stored, and where it ends up.

📮 The post office

You (an external entity) drop a letter in the box. A sorting station (a process) reads the address and routes it. It might sit in a mail bag overnight (a data store) before the next leg. Eventually it reaches another person (another external entity). The letter itself, moving between these, is the data flow — drawn as an arrow, always labelled with what's actually moving.

🔤 The four symbols

Four rules that make a DFD illegal — the exam loves these:
  • A data flow straight between two external entities — they only ever talk through a process.
  • A data flow straight between two data stores — same reason, a process has to move the data.
  • A data flow with no label — every arrow must say what's actually moving.
  • A process with no input ("a miracle") or no output ("a black hole") — a process that does nothing to nothing, isn't a process.

🔧 Challenge 1 — Library Book Borrowing System

Build a Level-1 DFD for: a Member can borrow a book and can search the catalogue. A Check Out Book process records the borrow in Book Records. A Search Catalogue process looks up Book Records and returns results to the Member. Use the toolbar to add shapes, connect them, and label every flow.

🔧 Challenge 2 — Pizza Ordering System

A Customer places an order with a Take Order process, which saves it to an Orders data store. A Prepare Pizza process reads the order from the store and sends the finished pizza back to the Customer. Build it from scratch.

🗄️ ENTITY-RELATIONSHIP DIAGRAMS

The data's own family tree

Where a DFD tracks data moving around, an ERD maps how the stored data relates to itself — this is the diagram that becomes your actual database tables.

🏫 The school office filing cabinet

A student is one kind of thing worth a file of its own. So is a course. So is a teacher. The interesting part isn't the files — it's the string connecting them: one teacher teaches many courses, and many students enrol in many courses. That connecting word is the relationship, and how many of each side can be on either end is the cardinality.

🔤 The symbols

Cardinality, plainly: "1" means exactly one of that entity is involved on that side of the relationship. "M" (many) means any number can be. A teacher teaching many courses but each course having one teacher is 1 : M. Students and courses, where each can have many of the other, is M : M.

🔧 Challenge — School Enrolment

Build the ERD for: a Teacher teaches many Courses, but each course has one teacher (1:M). A Student enrols in many courses, and each course has many students (M:M). Add the three entities, connect them, label each relationship, and click the cardinality badges until they read correctly.

Glossary

Data Flow Diagram (DFD) — a diagram tracing how data moves between external entities, processes, and data stores.

External entity — a person, organisation or system outside the system boundary that sends or receives data.

Process — a step that transforms or acts on data.

Data store — a place data is held at rest (a file, a database table) between processes.

Entity-Relationship Diagram (ERD) — a diagram showing how stored data entities relate to one another.

Entity (ERD) — a distinct thing the system stores data about (e.g. Student, Course).

Relationship — how two entities are connected (e.g. a Student enrols in a Course).

Cardinality — how many of one entity can relate to how many of another (1:1, 1:M, M:M).

Class diagram — shows a system's classes, their attributes and methods, and how classes relate.

Use case diagram — shows the actors of a system and the goals (use cases) they can perform.

Structure chart — shows a program broken into modules in a hierarchy, with data passed between them.

HIPO chart — Hierarchy plus Input-Process-Output; a structure chart with each module's inputs and outputs documented alongside it.

CASE tool — Computer-Aided Software Engineering software that helps build and manage these diagrams and specifications.
