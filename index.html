The big picture

One building, many blueprints

A house needs an architectural plan (rooms), an electrical diagram (wires), a plumbing diagram (pipes) and a structural diagram (beams). Each shows something the others can't. Software is the same: each diagram type answers a different question.

🎉 Planning a big lime

Class diagram = your guest list with details (who they are, what they bring, how they're related). Use case diagram = what guests will do (eat, dance, play dominoes, take photos). DFD = how the food moves (kitchen → serving table → guests → bin). ERD = how your contacts are organised (name, number, relationship, RSVP).

Class diagrams: blueprints for code

A class diagram shows the static structure of an object-oriented system: its classes (templates for objects), their attributes (data), their methods (operations) and the relationships between classes. Each class is a rectangle with three sections: name, attributes, methods.

Student
- studentID: int
- name: String
- email: String
- gpa: double
+ enrollCourse(c: Course): void
+ calculateGPA(): double
- validateEmail(): boolean

Visibility: + public (anyone) · - private (inside the class only) · # protected (the class and its subclasses).

The same class in Java
public class Student {
    private int studentID;
    private String name;
    private String email;
    private double gpa;

    public void enrollCourse(Course c) { … }
    public double calculateGPA() { … }
    private boolean validateEmail() { … }
}
You may see a stereotype above a class name in «double angle brackets», e.g. «ORM Persistable». It adds extra meaning, here that objects of the class can be saved to a database.

UML

Use case diagrams: who can do what

A use case diagram shows the interactions between users (actors) and the system. It answers "What can users DO with this system?", not how they do it.

🎬 A movie script outline

It lists the actors and the scenes each one appears in, but not the lines they say. The detailed script (the specification) comes later.

ComponentSymbolMeaningExample
Actor🧍 Stick figureA person, organisation or external system that interacts with the systemCustomer, Librarian, Bank
Use case⬯ OvalA goal or action the system performs for an actorPlace Order, Borrow Book
System boundary▭ RectangleWhat's inside the system vs outsideLibrary Management System
Association— LineThe actor takes part in that use caseMember — Borrow Book
«include»Dashed arrowOne use case always includes anotherPlace Order «include» Process Payment
«extend»Dashed arrowOne use case optionally extends anotherApply Coupon «extend» Place Order
«include» = ALWAYS happens (you can't place an order without paying). «extend» = SOMETIMES happens (a coupon is optional). The arrow for «include» points from the base use case to the included one; the «extend» arrow points from the optional extra to the base.

Data Flow Diagrams

Follow the data like a parcel

A DFD shows how data moves through a system: where it comes from, what processes transform it, where it is stored and where it ends up. It doesn't care about buttons, screens or the order things happen in, only the data.

📦 Tracking an online order

You (external entity) place an order → Process Order (process) receives the details → the Orders database (data store) saves them → the warehouse process picks and packs → the delivery process ships → you receive the parcel and a confirmation. Every arrow carries something named: "order details", "packing slip", "tracking number".

The four building blocks

External entity
A person, organisation or system outside the system that sends data in or receives data out. A noun. Like customers in a restaurant: not kitchen staff, but they give orders and get food.
Process
Transforms data: a verb + noun ("Record Loan"). Numbered 1.0, 2.0… Like a chef turning ingredients into a dish. Must have at least one input and one output.
Data store
Data at rest: a database, file or table. An open-ended rectangle labelled D1, D2… Like a filing cabinet: files go in, files come out.
Data flow
An arrow showing data moving, always labelled with what data (not how). Like a labelled parcel.

⚠️ The rules a DFD must obey

  1. Every process has at least one input and one output. (No input = a "miracle"; no output = a "black hole".)
  2. Every data store should have data going in and coming out; data can't just sit unused.
  3. External entities never talk directly to each other; they go through a process.
  4. Data never moves store → store or entity ↔ store without a process doing it.
  5. Every data flow is labelled. No mystery arrows.
  6. Processes are numbered in order: 1.0, 2.0, 3.0 at level 1; 1.1, 1.2 at level 2.

🔎 Why "through a process"?

A data store is just a filing cabinet. A filing cabinet can't open itself and walk a file over to another cabinet; someone (a process) has to do it. And a customer can't reach into the shop's database; the shop's system (a process) reads and writes it on their behalf.

Zooming in: DFD levels

🛰️ Context diagram (level 0)

The bird's-eye view: the whole system as one process, surrounded by all its external entities and the main data flows. No data stores; they're hidden inside. (Your school seen from a helicopter: one building, people coming and going.)

🗺️ Level 1 DFD

The floor plan: the single process is broken into its major processes (1.0, 2.0, 3.0…), and data stores (D1, D2…) appear. Same external entities as level 0. (Now you see classrooms, office, library.)

🔍 Level 2+

The room view: one level-1 process is broken down again; process 2.0 becomes 2.1, 2.2, 2.3. Rarely go past level 2 or 3; too much detail confuses.

🔄 Functional decomposition

Breaking a complex process into smaller sub-processes: "Make Dinner" → 1.1 Plan Menu, 1.2 Shop, 1.3 Prepare Ingredients, 1.4 Cook, 1.5 Serve. A primitive process is one simple enough that it needs no further breaking down ("Boil Water").

⚖️ Balancing

The data flows in and out of the system at level 0 must match the flows in and out of the level-1 diagram. If "Book Request" enters the context diagram, it must enter some process in level 1 too. Nothing appears or vanishes when you zoom.

🎮 Video-game maps

Context level = the world map. Level 1 = the regions (Forest, Desert, Castle). Level 2 = inside the castle (Throne Room, Armoury, Kitchen). Level 3 = the swords and shields in the armoury.

🛠️ The 7-step method for drawing any DFD

1. Read carefullyRead the scenario twice. Highlight.
2. External entitiesWho is outside but sends/receives data? (nouns)
3. ProcessesWhat actions transform data? (verbs)
4. Data storesLook for "database", "file", "records", "stored", "saved".
5. Data flowsWhat information moves? Label what, not how.
6. Context diagramOne process, all entities, no stores.
7. Level 1Split the process, add stores, keep it balanced.

Highlighter: steps 1–5 on a real scenario

Entity-Relationship Diagrams

The data's family tree

An ERD is a data-modelling tool for designing databases. A DFD tracks data moving; an ERD maps how stored data relates to itself. This is the diagram that becomes your actual database tables.

📱 Your phone contacts

Entities: the kinds of things you store (Contacts, Groups, Calls). Attributes: details about each (name, number, birthday). Relationships: how they connect (a Contact belongs to a Group; a Contact made a Call). Cardinality: one person can belong to many groups, and one group holds many people.

Entity (rectangle)
A thing we store data about (a noun). Becomes a table. One specific student, "Shanice", is an instance (a row).
Attribute (oval)
A fact about an entity. Becomes a column. "Address" is usually an attribute, not its own entity.
Primary key (underlined)
Uniquely identifies each instance: unique, never empty, doesn't change. Two students may share a name but never an ID.
Relationship (diamond)
How entities connect, usually a verb: Customer places Order; Teacher teaches Course.

🔢 Cardinality: the part everyone gets wrong

Cardinality says how many instances of one entity can relate to instances of another. Always ask two questions, one from each side:

1 : 1 one-to-one

Person ↔ Passport · Country ↔ Capital · Car ↔ Licence plate · Order ↔ Payment

1 : M one-to-many

Customer → Orders · Department → Employees · Mother → Children · Teacher → Courses

M : N many-to-many

Students ↔ Courses · Actors ↔ Movies · Doctors ↔ Patients · Products ↔ Orders

🎺 The steel band

1:1: each player has one assigned locker, each locker one player. 1:M: one band leader leads many players; each player has one band leader. M:N: many players play many pans (Shanice plays tenor and double seconds; the tenor is played by Shanice and Kevin).

🔗 Composite key

When two attributes together form the primary key because neither alone is unique. Flight number AA100 flies every day, and many flights share a date, but Flight_Number + Date is unique.

🔒 Referential integrity

A rule that keeps relationships consistent: a foreign key must point to something that exists. You can't reserve a book that isn't in the catalogue, or record an enrolment for Student 999 if there is no Student 999.

Program design

Structure charts & HIPO charts

DFDs show data. Structure charts show control: which module is the boss of which, and what they pass each other.

🏢 The company org chart

The CEO (main module) delegates to managers (sub-modules), who delegate to staff (lower modules). Data goes down with each instruction and results come back up.

📋 HIPO: Hierarchy plus Input-Process-Output

A documentation tool developed by IBM. It has two parts: (1) a Visual Table of Contents (VTOC), the numbered hierarchy of modules, and (2) an IPO diagram for each module listing its Inputs, Processing and Outputs. Great for testing (you know exactly what goes in and out) and for explaining to non-technical people.

🍳 A recipe book

The table of contents lists the dishes (main course, sides, dessert) in a hierarchy. Each recipe page lists ingredients (input), steps (process) and the finished dish (output).

Design toolkit

Standard interfaces & CASE tools

🔌 The USB port

Any USB mouse, keyboard or flash drive plugs into any USB port, because they all follow the same standard. A standard interface in software is a predefined agreement for how components communicate: what data is exchanged, its format, which operations exist and how errors are handled.

❌ Without a standard interface

if (provider == "PayPal")
  paypal.sendPayment(amt, email, id);
else if (provider == "Stripe")
  stripe.charge(card, amt, number);
// every provider is different!

✅ With one

interface PaymentProcessor {
  processPayment(amount, customerID, orderID)
  refundPayment(transactionID)
}
processor.processPayment(99.99, "C123", "O456");
// works with ANY provider

Benefits: interoperability, flexibility (swap components easily), maintainability (changing one module doesn't break others), reusability and independent testing.

Which interface type?

🛠️ CASE tools: power tools for analysts

Computer-Aided Software Engineering tools automate parts of the life cycle: drawing diagrams, generating code from designs, managing requirements, version control, testing and project management. Like a power drill versus a screwdriver.

⬆️ Upper CASE (front-end)

Planning, analysis and design: requirements, diagrams, prototypes. draw.io, Lucidchart, ERDPlus, Visio

⬇️ Lower CASE (back-end)

Implementation and testing: code generation, testing and debugging. Visual Paradigm and StarUML code generation, PlantUML

🔄 Integrated (I-CASE)

The whole life cycle in one environment. Enterprise Architect, IBM Rational

✅ Benefits
  • Faster diagrams and documentation
  • Consistency checks (e.g. ERDPlus flags bad cardinality)
  • Code generated from designs
  • Team collaboration and version control
⚠️ Risks
  • No standardisation; tools may not be compatible
  • Vendor lock-in
  • Unrealistic expectations: tools don't replace skilled analysts
  • High start-up costs and a learning curve
Free tools to practise at home: draw.io (diagrams.net) for DFDs and everything else, ERDPlus for ERDs (it can even generate SQL), PlantUML for diagrams written as text. Mitigate the risks by choosing tools that export to standard formats and starting with free ones.
